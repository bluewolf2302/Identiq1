# Guideline PDF review (Phase 3)

## Temporary workflow

- The Guideline PDFs tab is part of the existing Knowledge Hub. The PDF
  workflow does not convert records into `KnowledgeEntry`.
- Document ID, title, and version ID are entered explicitly. The PDF is sent to
  the temporary `POST /api/guideline-review/extract` Route Handler. That handler
  uses `extractGuidelinePdfText`, returns the validated extraction result, and
  does not store the uploaded PDF.
- `pdfjs-dist` is externalized from the App Router server bundle so its
  package-relative worker can be resolved by Node.js during route processing.
- Section and rule IDs created by the UI are ephemeral in-memory identifiers;
  document and version IDs are never generated by this flow.
- A reviewer selects text from one extracted page and supplies its section
  name to create a rule. The selection's exact text and JavaScript UTF-16
  offsets become the original text and source excerpt. There is no OCR,
  automatic rule segmentation, or AI classification.
- Rule edits and `PENDING_REVIEW` / `ACCEPTED` / `REJECTED` decisions are held
  by `createInMemoryGuidelineReviewService`. The service is a client-side,
  module-scoped in-memory instance: drafts are lost on a full browser reload,
  browser close, or module restart; they are not shared between users or
  devices.
- Per-rule acceptance is not document-version approval. This UI has no final
  approval operation and its drafts are not eligible for governance-engine
  retrieval.

## Service and future integration points

The UI depends on the `GuidelineReviewService` interface in
`lib/guidelines/review-service.ts`, not on `IdentiqProvider`, `KnowledgeEntry`,
or a persistent repository. A future adapter can implement this interface
after the team confirms its persistence and service contracts. The temporary
extraction Route Handler is an implementation detail of the current in-memory
adapter, not a proposed permanent backend API. No new application page or
navigation item is required; integration belongs in the existing Knowledge Hub.

Before replacing the temporary adapter, the infrastructure owners need to
agree on document/version identifiers, where the original PDF and extracted
pages live, server-side validation limits, review-change persistence, and
separate document approval/audit semantics. Authentication, organization
isolation, storage provider, and API routes are intentionally not selected
here.

Approved-rule retrieval is also out of scope. When the approved-version
contract is defined, integrate it through `BrandKnowledgeRepository` and the
existing brand-context retrieval boundary; do not make `ACCEPTED` rules
available to the engine by themselves.
